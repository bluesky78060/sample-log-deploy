동기화 안정화 정밀 비교

메인 프로젝트(sample-log-electron) vs 테스트 프로젝트(sample-log-electron-test)
작성일 2026-06-28 대상: Firestore 동기화 계층 4파일 + sync-utils + BaseSampleManager 방식: 함수·로직 단위 라인 대조
한 줄 결론. 동기화 계층은 한쪽이 일방적으로 우위가 아니라 양방향 트레이드다. 테스트는 네트워크 회복성(재시도·오프라인 큐·취소)이 강하고, 메인은 불완전 캐시 읽기 시 로컬 데이터가 일시적으로 사라지는 현상을 막는 안전장치(SAMPL-1-80)를 갖췄다. 소비 흐름 추적 결과 이는 영구 cross-device 손실이 아니라 일시적 로컬 소실(다음 정상 읽기 시 자가 치유)로, 심각도 MEDIUM의 실질 격차이며 테스트에 빠져 있다.

※ 이전 세션에서 줄 수·키워드 카운트 기반으로 "동기화 격차 없음, 테스트가 더 견고"라고 보고했으나, 본 라인 대조 결과 그 결론은 이 안전장치 축에서 틀렸음을 정정한다.

MEDIUM① 메인에만 있음 — fromCache 기반 cross-device 삭제 보류 (SAMPL-1-80)

양쪽 smartMerge의 "로컬에만 있는 항목" 처리 분기가 핵심 차이다. 로컬에 있지만 클라우드 응답에 없는 항목을 삭제로 볼지 보존할지를 결정한다.

실제 위험 시나리오 — 소비 흐름 추적 결과

오프라인·일시 단절·경합 상태에서 Firestore가 캐시(불완전) 응답(fromCache=true)을 반환하면, 테스트는 "클라우드에 없음 = 다른 기기에서 삭제됨"으로 오판하고 syncedAt이 있는 멀쩡한 로컬 레코드를 병합 결과에서 떨어뜨린 뒤 localStorage에 덮어쓴다(BaseSampleManager.ts:545~566).

단, 실제 blast radius는 제한적이다: 클라우드(서버)에는 레코드가 보존된다(batchSave는 merge:true라 누락 문서를 삭제하지 않고, 명시적 delete()는 사용자 액션일 때만 호출됨). 따라서 영구 손실이 아니라 "로컬에서 일시적으로 사라졌다 다음 정상 읽기 때 다시 나타나는" 자가 치유 현상이다. 다만 PER-9 TTL 캐시가 그 불완전 응답을 TTL 동안 재사용하므로, 오프라인·경합이 지속되면 한동안 데이터가 보이지 않아 사용자가 데이터 유실로 오해하고 재입력(중복 생성)하는 2차 사고를 부를 수 있다.

이 안전장치는 3개 파일에 걸친 체인이며 테스트는 전부 누락했다.

SAME③ 양쪽 동일 — 충돌·timestamp 핵심 로직

이 5개 장치는 메인·테스트가 완전히 동일해서 두 프로젝트의 동기화 "기반"은 같은 수준이다. 각 장치가 어떤 동기화 실패를 막는지 아래에 풀어 설명한다.

1. serverTimestamp() + { merge: true } — 시계 충돌 & 부분 덮어쓰기 방지

project/src/shared/firestore-db.ts:214~221
const docData = {
  ...data,
  id: normalizedId,
  updatedAt: serverTimestamp()   // 서버 시각
};
if (!docData.createdAt) docData.createdAt = serverTimestamp();
await db.collection(...).doc(...).set(docData, { merge: true });
  • serverTimestamp(): 클라이언트 로컬 시계가 아니라 Firestore 서버 시각을 기록. 여러 기기 시계가 어긋나 있어도 "누가 더 최신인가" 판정이 서버 기준 단일 타임라인으로 통일됨 → 시계 차이로 인한 최신성 오판 제거.
  • { merge: true }: 문서를 통째로 덮어쓰지 않고 전달한 필드만 갱신. A 기기가 일부 필드만 바꿔도 B 기기가 채운 다른 필드가 안 날아감. (①의 "캐시 삭제 보류"가 성립하는 전제 — merge라서 누락 문서가 안 지워짐.)

2. createdAt → updatedAt → 0 오름차순 로컬 정렬 — 정렬 누락 방지

project/src/shared/firestore-db.ts:314~320
documents.sort((a, b) => {
  const aTime = a.createdAt?.seconds || a.updatedAt?.seconds || 0;
  const bTime = b.createdAt?.seconds || b.updatedAt?.seconds || 0;
  return aTime - bTime;
});
  • 폴백 체인: createdAt 없으면 updatedAt, 그것도 없으면 0. timestamp 필드가 빠진 구버전 문서도 정렬에서 탈락하지 않고 맨 앞(0)에 배치 → 항목이 화면에서 사라지는 일 방지.
  • ?.seconds: 아직 확정 안 된(pending) serverTimestamp 문서도 안전하게 0으로 처리.

3. orderBy 제거 — "필드 없으면 제외" 함정 회피

project/src/shared/firestore-db.ts:661 (subscribeToChanges)
// orderBy 제거: updatedAt이 없는 문서가 제외되는 문제 방지
const querySnapshot = await db.collection(collectionName).get();
  • Firestore에서 .orderBy('updatedAt')로 서버 정렬을 걸면 그 필드가 없는 문서는 결과에서 통째로 빠진다(Firestore 기본 동작). 정렬하려다 데이터가 누락됨.
  • 그래서 서버 정렬을 포기하고 전체를 가져온 뒤 2번처럼 로컬 정렬. 정렬 정확도를 약간 양보하되 "데이터 누락 0"을 보장하는 트레이드. 동기화에선 누락이 정렬보다 치명적이라 올바른 선택.

4. 삭제 3단계 + 멱등 삭제 — ID 타입 불일치 & 거짓 실패 방지

project/src/shared/firestore-db.ts:374~400
// 1차: 문서 ID로 직접 삭제
if (directDocSnap.exists) { await directDocRef.delete(); return true; }
// 2차: id 필드 == 문자열 로 쿼리
let q = await col.where('id', '==', stringDocId).get();
// 3차: 문자열로 못 찾으면 id == 숫자 로 재시도
if (q.empty && !isNaN(numericDocId)) q = await col.where('id', '==', numericDocId).get();
// 대상 없음 = 이미 삭제됨 = 성공 (멱등)
if (q.empty) return true;
  • 3단계 탐색: id가 문자열("123")·숫자(123)로 혼재된 상황을 모두 커버. 한 타입만 쿼리하면 못 지우는 좀비 데이터가 생기는데 그걸 방지.
  • 멱등 삭제: 지울 대상이 이미 없으면 에러가 아니라 성공으로 처리. 미업로드 항목 삭제 시 "삭제 실패"로 잘못 뜨는 거짓 실패를 막아 재시도 루프가 헛돌지 않음.

5. 실시간 subscribe의 fromCache 전달 — 실시간 경로의 신뢰도 표시

firestore-db.ts:663 / storage-manager.ts:441
.onSnapshot((snapshot) => {
  ...
  callback(documents, snapshot.metadata.fromCache);  // 신뢰도 동반
});
// storage-manager 소비:
if (!fromCache) syncStatus.lastSyncTime = new Date();  // 서버 확정분만 기록
  • 실시간 스냅샷이 캐시에서 온 것인지(fromCache=true) 콜백에 같이 넘김. 캐시 응답으로는 lastSyncTime을 갱신하지 않아 "마지막 동기화 시각"이 거짓 최신화되지 않음.
  • 핵심: ①의 격차는 일회성 getAll 경로에만 있다. 이 실시간 subscribe 경로는 테스트도 fromCache를 제대로 인지한다. 즉 테스트가 fromCache 개념을 모르는 게 아니라, 로드 시점(getAll)에서만 그 플래그를 버리는 게 ①의 정확한 빈틈이다.

정리 & 권고

이전 결론 정정

줄 수·키워드 카운트는 회복성 코드량 때문에 테스트가 커 보였을 뿐, 데이터 무결성 안전장치는 메인이 우위다.

  • 테스트 우위: 네트워크 회복성(재시도 / 오프라인 큐 / 취소)
  • 메인 우위(실질 격차, MEDIUM): fromCache 삭제 보류 — 불완전 캐시 읽기 시 로컬 데이터가 일시적으로 사라지는 현상 방지(자가 치유되지만 사용자 혼란·재입력 2차 사고 유발).

적용하면 더 좋은가? — 권장(단, 성격 정확히)

적용 가치 있음. 다만 이유는 "치명적 손실 방지"가 아니라 "혼란스러운 데이터 깜빡임 제거 + 메인 라인과 정합"이다.

  • 좋아지는 점: 오프라인/순간 단절 시 멀쩡한 데이터가 화면에서 사라지는 episode 제거 → 사용자 재입력(중복) 2차 사고 차단; 두 코드베이스 발산(유지보수 부담) 해소; 메인의 검증된 패턴 재사용이라 비용 저렴.
  • 받아들이는 트레이드(의도된 것): 진짜 cross-device 삭제 반영이 약간 늦어짐(다음 정상 읽기까지 보류). 저동시성·소수 기기 농업 시료 대장에선 데이터 보존 ≫ 즉시 삭제 전파라 올바른 트레이드.

MRL에 이어 이식할 가치가 있는 두 번째 실질 격차다. 권장 이식 범위는 3파일:

#파일변경 내용
