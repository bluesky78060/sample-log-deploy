## 3. 결함과 처리

### 🟠 F-1 — F 없는 성토 레코드가 있으면 일반 등록이 영구히 막힌다 (재현 PA·PG, 수정됨)

`receptionBaseKey`(reception-number.ts)가 F 없는 성토 레코드를 일반 풀에서 뺐다. 그러면 일반 채번이 그 번호를 다시 내는데, 폼 중복 검사(soil-script.ts `submitForm`, 본번만 비교)는 그 번호를 거부하고 「N번으로 변경」이 같은 N을 낸다.
이번 커밋의 회귀는 아니다(d943451이 동작 불변으로 고정한 규칙). 코디네이터 질문 「레거시 5(성토, F 없음)의 채번」에 대한 답이 이것이다.

선택지 두 개 중 **F 없는 성토가 일반 번호를 점유한다**(양쪽 풀에 든다)로 고쳤다. 다른 쪽(폼 중복 검사를 풀 인식으로)은 같은 경지구분에 `5`(성토)·`5`(논)이 공존하게 하는데, 일괄 완료(soil-script.ts:4328)가 풀을 번호의 F 접두로만 보고 목록도 둘 다 `5`로 보여 분석결과 매칭 키가 충돌한다.
바뀐 기대: `reception-number.test.ts` 「일반 채번은 F 접두가 없는 성토 레코드도 제외」 → 「…번호를 건너뛴다」(2 → 21), `reception-base-key.test.ts`·`soil-import-preview.test.ts`의 같은 전제 3곳. 성토 채번·흙토람 형제 판정은 바뀌지 않는다(`isFillLog`는 그대로).

### 🟠 F-2 — 폼이 번호 풀과 어긋나는 구분을 저장한다 (재현 PB, 수정됨) — 작업자가 남긴 근본 원인

`subCategory = parcel.category || 상단값`(신규·그룹 수정·단일 수정 3경로). 메인 프로젝트(`soil-script.js`)는 상단값을 저장한다 — TS 포팅에서 갈라진 것이다. 상단 논 + 필지 성토 → `'1'/성토`(F 없음, F-1 유발), 상단 성토 + 필지 논 → `F1/논`(P1). 둘 다 가져오기가 결정 3으로 거부하는 모양을 앱이 만든다.
수정: `_formPoolConflict` — 번호와 상단 구분이 어긋나면(`importRowConflict` 재사용), 또는 일반 번호인데 필지 구분이 성토면 토스트로 막고 저장하지 않는다. `_recordSubCategory` — F 번호면 레코드 구분은 성토(필지 카드 값은 필지에 남는다). 세 경로에 같이 넣었다.

### 🟡 F-3 — 덮어쓰기의 구분 보호가 `isFillLog` 이전 기준이다 (재현 PC, 수정됨)

`keepSubCategory = (src === '성토') !== (t.subCategory === '성토')` — e220a61이 풀 판정을 `isFillLog`(F 접두 포함)로 바꿨는데 이 가드만 구분 문자열로 남았다. 「한 방향만 고치면 반대쪽이 남는다」는 이 시리즈의 패턴 그대로다. `F1/논`에 `F1/성토`를 덮어써도 논으로 남아 P1 산물을 고칠 길이 없었다.
수정: `isFillImportRow(번호, 구분) !== isFillLog(target)`. 「옛 성토 7의 구분을 일반으로 바꾸지 않는다」는 그대로 지켜진다(변이 MF3에서 확인).

### 🟡 F-4 — 번호가 정확히 같은 레코드가 여러 건이면 첫 건만 갱신 (재현 PD, 수정됨) — m-3

어느 건이 바뀌는지 배열 순서가 정하고 미리보기는 「중복」이라고만 한다. 데이터 파괴는 아니지만 분석결과 매칭 키를 임의로 고르는 것이라 결정 「여럿이면 고르지 않는다」에 맞춰 `ambiguous`로 돌렸다(3줄). 배치 안에서는 같은 번호가 두 번 와도 두 번째가 첫째를 갱신하므로 중복 레코드가 새로 생기지는 않는다.

## 4. 보고만 (수정하지 않음)

- 🟡 **레거시 F 없는 성토를 앱이 내보낸 파일은 되가져올 수 없다**(PE: `5` + 구분 성토 → 오류). 결정 3의 귀결. F-2로 앱이 더는 그런 레코드를 만들지 않으므로 남는 것은 기존 데이터뿐이다. 필요하면 번호를 F로 고치는 일회성 정리가 별 티켓.
- 🔵 배치 역순(`7-1` 다음 `7`)에서 `7`이 배치 안 `7-1`에 접힌다(PF). 결정 2가 「같은 배치에서 앞서 추가된 것」을 기존으로 치기 때문. 미리보기가 보여준다.
- 🔵 `importRowConflict`가 `'-'`를 실제 구분으로 본다: F 번호 + 구분 `'-'` 행은 오류다. 안전한 방향이고 폼은 F 레코드에 항상 성토를 넣으므로 두었다.
- 🔵 기존 작물 1개(단위 없음)에 `'고추, 콩'` 행을 덮어쓰면 이름이 `'고추, 콩'`인 작물 1개가 된다. 사용자가 실제로 바꾼 것과 구분할 수 없다.
- 다필지 그룹 레코드 덮어쓰기는 `parcels[0]`만(작업자 보고와 같음).
